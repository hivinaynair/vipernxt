# Requirements discovery: research and changes

The existing field contract is useful, but implementation readiness needs a reconciled packet covering the domain, rules, failure behavior and acceptance evidence. The strengthened workflow defines that packet and its review gates; it cannot guarantee an exhaustive interview or unattended production delivery.

Researched 2026-09-30. Source branch: `staging` at `bbd3357f717b752d6f0075e263498fd8d9672f14`. Official public documentation sites returned proxy HTTP 403; the sources below were read through their official GitHub repositories. No paid agents or external deployments were used.

## Gaps addressed

The old workflow already covered observed examples, stable surface IDs, basic entity/state modeling, access foundations and pinned MVP spine coverage. The main omissions were a unified applicability/reconciliation review, deeper entity identity/lifecycle invariants, explicit trace from business decisions to cases, and consistent treatment of operating/integration requirements. A stale question-bank instruction also asked for another skill selection after design approval, contradicting `/next`'s authorized progression.

The new [readiness guide](../../.agents/skills/shape/requirements-readiness.md) links each applicable area to one canonical contract. The [model contract](../../.agents/skills/ontology/model-contract.md) settles identity, attribute semantics, relationships, ownership, transitions and lifecycle before schema decisions. The [review template](../../.agents/skills/shape/requirements-review-template.md) records coverage, evidence/assumptions, traceability, findings and walkthroughs. The [acceptance guide](../../.agents/skills/shape/requirements-acceptance.md) requires resulting state and forbidden effects as well as visible behavior.

Shape now drafts domain decisions before approving policy. Ontology and journey expansion preserve that meaning; `/next` reconciles finalized contracts before wave 0 and the whole MVP before unattended handoff. Design approval can cover the packet in one decision. First-working-clip acceptance remains separate. Builders choose internal technical details; they return material business gaps to `/next`. Changed requirements reopen only affected contracts, cases and dependent jobs.

## How to assess quality

Use an observed ordinary/incomplete/exception walkthrough, then applicable boundary, denial, duplicate, conflict and outage cases. A proposed required field must be knowable when entry occurs; a relationship must be populatable; an action must have an authorized owner and valid state transition. Review both directions: every approved promise has a case and planned slice, and every planned field or side effect has an approved purpose.

The illustrative invoice cases in the acceptance guide are synthetic specifications, not executed software evidence. A desk audit of the earlier synthetic Claimline ontology and data surfaces confirms that its clip already settles unique case/invoice identifiers, non-null clerk-validated POD booleans and derived status; those decisions should not be re-asked. Its read-only clip excludes write-conflict and live-sync behavior. A future import/write-enabled MVP would need decisions about identifier uniqueness across imports, contradictory source updates, stale records and conflict recovery; the clip's exclusions cannot certify that scope. This is a manual review, not new customer research or proof of a requirements validator.

Track questions discovered during implementation, business rules guessed by builders, requirements-related repair rounds, acceptance failures, escaped defects and user corrections. Improvements should reduce those outcomes across real engagements. A longer questionnaire or a fully populated table alone is not success.

Validation on this staging-based documentation branch: `bun test` completed with 333 passes and zero failures; type checks passed; all 22 newly introduced local Markdown links resolve; `git diff --check` passed. Boundary/token/journey commands also exited successfully, but this bare kit has no product app/spine, so those checks do not demonstrate requirements coverage or product behavior. No new customer interview, paid factory run or hosted deployment was performed.

## Limits and next implementation step

This change strengthens skill instructions and contract templates. No new runtime schema, discovery validator, automatic approval, merge or deployment behavior is added. Existing hooks check shape status; Eve validates the pinned spine/catalog and execution evidence. Neither verifies every row of the new review or proves exhaustive discovery. A separate deterministic validator could enforce references, case mappings and unresolved-item blocking, with migration rules for existing engagements; it would still require customer walkthroughs and behavioral verification.


## Implementation following the repository review

The supplied Eve template was inventoried at `6bc5febab95de4c05fa08b164f544650f6aa11aa`: 98 tracked files, including all 73 TypeScript files and its prompts/configuration/documentation. The review covered source behavior; it did not execute its paid agents or validate every transitive lockfile package. Its typed station contracts, independent actual-diff review, signed event boundary and bounded CI repair informed this implementation. We retained ViperNxt's pinned coverage and compare-and-swap state, made approval hash-bound, removed reviewer ID/command coercions that could manufacture acceptance, and added durable CI/deployment reconciliation. Unlike the reference's permissive unresolved-plan choices, ViperNxt holds missing business policy. No template SDK upgrade, public Blob artifact store or production branch policy was copied.

See [requirements packet](requirements-packet.md) for the structural gate and [Eve automation](../../deploy/eve/AUTOMATION.md) for the implemented recovery/delivery behavior. Local tests cover invalid approval/review, stale CI, duplicate repair, exact candidate branch updates, uncertain dispatch restart, mismatched deployment provenance and budget exhaustion. Hosted deployment evidence remains outstanding; a successful test fixture or build is not that evidence.
